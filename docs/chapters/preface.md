# 前言：VibeKaggle 不是用
AI
写代码
## 为什么要写这本书

2026 年，Google 和 Kaggle 联合发布了一份名为《The New SDLC With Vibe Coding》的白皮书。这份文件里有一个判断让我印象极深：**随意提示和真正的工程之间，分水岭是验证。**

这句话听起来可能有点抽象，但如果你在 Kaggle 上跟着大模型（LLM）做过几场比赛，就会立刻明白它的意思。很多人第一次用 Cursor、Claude Code 或者 GitHub Copilot 做 Kaggle 时，体验通常是这样的：你告诉模型\帮我写一个
XGBoost
基线\，模型吐出一堆代码，你跑通了，提交了一次，分数还不错。然后你让模型\再优化一下特征工程\，模型又吐出一堆代码，你跑通了，提交了，分数反而掉了。你让模型\修复一下过拟合\，模型改了参数，你又跑了一遍，分数还是不稳定。最后你发现，自己跑了几十个实验，排行榜分数却在原地踏步，甚至倒退。

**问题不在模型能力上，而在于你没有给模型装上\护栏\。**

白皮书进一步提出了一个对全书具有组织意义的分解：**Agent = 模型 + Harness，比例大约是 10/90**。模型只占 10%，Harness——指令、工具、MCP 服务器、沙箱、编排、护栏、可观测性——占 90%。大多数 Agent 失败，是**配置失败**，不是模型能力失败。

这意味着 VibeKaggle 的核心技能不是\写更好的提示词\，而是**设计更好的 Harness**：固定验证协议、规范工件命名、限制提交预算、约束工具集。

## 一个真实的冠军案例

NVIDIA 的 Chris Deotte 在 2026 年 3 月的 Kaggle Playground 客户流失预测竞赛中，用 GPT-5.4 Pro、Gemini 3.1 Pro 和 Claude Opus 4.6 三个 LLM Agent 生成了超过 60 万行代码，运行了 850 个实验，构建了一个由 150 个模型组成的四级 Stack 并获得第一名。

他的工作流中贯穿一条纪律：**每个实验的 OOF（Out-of-Fold）和测试预测都必须保存为可组合的工件文件**。没有这条纪律，850 个实验只会制造不可复现的混乱。

与此同时，Agent 的能力边界不是固定的。MLE-Bench 的基线显示纯自动 Agent 的奖牌率约为 16.9%，但在 Harness 设计良好的条件下，先进系统已经能把这一数字推到远高于此的水平。**边界的位置取决于 Harness 设计，而非模型选型。**

人的不可让渡角色，是在 Agent 的高吞吐量之上做**判断**——判断哪个方向值得深入、验证方案是否系统性偏差、工件是否可信、是否值得消耗一次提交。

## 本书的组织方式

这本书的组织方式与传统的 Kaggle 教程根本不同：

- **工件规范不是附录，而是第 2 章的基础协议**；
- **自动基线不是可选项，而是每一个代表比赛章的第一个动作**；
- **Agent 协作不是策略章节的话题，而是贯穿全书的操作模板**。

每一章都遵循同一个循环：**自动基线工件 → 人设定验证纪律 → Agent 批量实验 → 人审查工件并选择**。

## 面向读者

- 会一点 Python（知道什么是列表、字典、DataFrame、函数）；
- 了解基本的机器学习概念（训练集/测试集、过拟合、交叉验证）；
- **从未参加过 Kaggle 竞赛**，或者参加过但停留在\手动跑
Notebook\阶段；
- 想学会**如何设计并运行一条人机协作的竞赛工作流**，而不是\亲手做完每一个步骤\。

## 如何阅读

- 第 1-3 章是入门必读，建议按顺序动手跑通；
- 第 4-6 章是表格竞赛核心，建议配合 Playground 系列练习；
- 第 7-18 章按模态分类（时序、图像、文本），可按兴趣跳读；
- 第 19-23 章是进阶与迁移，适合想把比赛经验带入实际项目的读者；
- 附录是工具速查，随时翻阅。

## 约定

书中所有代码均为**可运行的完整 Python 脚本**，关键概念配有 **Mermaid 图表**，重要交互包含**大模型对话记录**（三个反引号包裹，含思考过程）。术语表见附录 H。

---

> **一句话总结**：VibeKaggle 不是让 AI 帮你写代码，而是让你设计一套**让 AI 在护栏内高吞吐产出可验证工件**的系统。你负责判断方向，AI 负责填充细节。
